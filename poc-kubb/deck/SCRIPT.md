# Kubb talk: spoken script (8 min) + audience Q&A

Written for a mixed audience (FE, BE, QA), pleno to senior. Delivery language: English.

How to use this: it is a **flow, not a text to read**. Each beat has the idea, a sample way to say it, and a bridge to the next beat. Say it in your own words. The slide notes (in the .pptx) have the short read-aloud version.

## 0:00 Opening (slide 1, just "Kubb")

Go straight to the point. No rhetorical question.

> "Hi everyone. Today I will show you a tool called Kubb. It writes the API code for you, from the spec.
> We have eight minutes: what it is, how it works, a live demo in VS Code, and when you should use it, and when you should not."

Bridge: "So, what is it?"

## 0:45 What it is (slide 2)

One sentence, then let the chips on the slide do the work.

> "Kubb is an open source code generator, MIT licensed. You give it an OpenAPI spec, and it writes the code around your API: TypeScript types, typed clients, React Query or Vue Query hooks, Zod schemas, mock handlers for MSW, Faker data, even Cypress tests.
> Two things I like. One: you choose what you want with plugins, in a single config file. Two: the output is plain files in *your* repo. No magic at runtime. You can read every line."

Then speak to the room, one role at a time:

> "Backend: your spec stops being documentation and becomes a real contract. Frontend: no more types written by hand. QA: mocks and test data come from the same spec."

Bridge: "And how does it do that? Less magic than you'd think."

## 1:45 How it works (slide 3)

Trace the diagram left to right with your finger. Keep it to 60 seconds.

> "Think of a pipeline. An adapter reads your spec once and resolves all the references. That gives you an AST, a neutral tree of schemas and operations. It doesn't know anything about Axios or React.
> Then plugins take that same tree, and each plugin owns one output. One makes types, one makes the client, one makes Zod.
> The point: the spec is parsed once and feeds many plugins in one run. Want a new output? Add a plugin. You don't touch the others. And if nothing fits, you can write your own."

Bridge: "Enough slides. Let me show you."

## 2:45 Live demo (switch to VS Code, about 2 minutes)

Before the talk: `npm run demo:reset`, `nvm use 22`, zoom in, tabs open: `petStore.yaml`, `kubb.config.ts`, `src/index.ts`.

**Moment 1: the setup (about 40s)**

Open `petStore.yaml`.
> "This is a tiny Petstore spec. One endpoint, get a pet by ID, and one schema, Pet, with an id and a name."

Open `kubb.config.ts`.
> "And this is the entire config. The spec, an output folder, and three plugins: types, client, Zod. That's it."

Open `src/index.ts`.
> "Here's some code that wants to call that endpoint. It's all red, because none of the generated code exists yet."

**Moment 2: generate (about 40s)**

Run `npm run generate`.
> "Watch the left side." [pause while it runs]
> "About 200 milliseconds. Nine files. And the red is gone."

**Moment 3: look inside (about 30s)**

Open `models/Pet.ts`, then `clients/getPetById.ts`. Point at the header.
> "Here's the type, here's the client. And look at the first lines in every file: 'Generated by Kubb, do not edit manually'. That's the deal. You never edit these. You change the spec and regenerate."

If someone looks puzzled by `bigint`, say: "Yes, int64 becomes bigint by default. There's an option for that, I'll come back to it." (See Q&A.)

**Closing the demo (optional, about 15s). No editing, just say it.**

> "If the backend adds a field, we change the spec, run generate again, and the types follow."

Bridge back to the slides: "That's the whole idea. Now, is it the only tool that does this?"

If anything breaks: stay calm, say "Let me show you the backup", go to slides 7 and 8 (hidden: in slideshow type `7` then Enter) or play the video. A calm switch looks more professional than a long debug.

## 5:30 Compare, trade-offs, and "why not Claude?" (slide 5)

Don't read the table. Pick three cells.

> "There are good alternatives. Orval is the closest in breadth. HeyAPI has nice runtime validation. openapi-typescript is great, and the fastest, if you only need types.
> Where Kubb stands out is breadth: it's the only one in this table that also generates Cypress tests and Redoc docs.
> Now the honest part. OpenAPI 3.2 support is partial. Some AI-related features are on the paid plan. And the speed and memory numbers come from Kubb's own benchmarks, so test it on your own spec before you believe me."

Then say the question out loud before someone asks it:

> "Now, someone may ask: why not just use Claude for this? Good question. But there is an important difference. **Kubb is a deterministic code generator. Claude is an AI that interprets and writes code.**
> With Kubb, the same spec gives the same code, every time. It runs on your machine, in milliseconds, and it is easy to review in a pull request. With an AI, the result can change from one run to the next, so you check it again every time.
> And there is the cost. Every time an AI writes a client, it spends tokens, for each endpoint, again and again. Kubb spends zero tokens. You only spend time once, to write the config.
> So they work well together. Use Kubb for the boring, repeatable layer. Use Claude for the business logic. Kubb even has an MCP server, so Claude can call it."

Bridge: "So, should you use it?"

## 7:00 Close (slide 6)

> "Use it when you have an OpenAPI spec, the API changes often, and several teams use it. Skip it when you have a few stable endpoints, or no spec and no plan to write one.
> The POC from today is on my GitHub, in the poc-kubb folder, with the script.
> Thank you. Questions?"

# Audience Q&A

Tags: **[docs]** comes from the Kubb docs I read. **[tested]** I ran it in the POC. **[opinion]** my recommendation, not a Kubb claim. **[not tested]** exists per the docs, but I did not try it.

If you don't know: "Good question, I haven't tested that. I'll check and share it in the channel." That is a fine answer.

## General

**Why not just write the types by hand?**
For three endpoints, you can, and Kubb is overkill. As endpoints, consumers and changes grow, hand-written types drift from the real API. A generated layer makes the spec the single source of truth. [opinion, matches the docs' "when not to use" list]

**Why not just ask Claude (or another AI) to write the client?**
They solve different problems. Kubb is a deterministic generator: the same spec gives the same output, locally, with no token cost, and the diff is easy to review. An AI interprets and writes code, so output can vary between runs and you must review it each time, and every client costs tokens, again for each change. Use Kubb for the repeatable layer, and an AI for logic that needs judgment. The docs also describe an MCP server and a Claude Code integration, so they can work together. [docs for MCP and Claude integration, opinion for the rest, not tested together]

**Is it free?**
Open source, MIT. Some things need a paid plan: the docs say API skills for AI tools require Pro. [docs]

**Is it mature? What is the risk?**
It is on version 5.x, with a changelog and a migration guide in the docs. I can't vouch for stability beyond my small POC. Pin versions, and start with one non-critical service. [docs, opinion]

**How long does adoption take?**
The POC took minutes to get working. For a real project, the effort is not the tool, it is the quality of your spec. [opinion]

**We have no OpenAPI spec. Can we use it?**
Not a good fit. The docs list "no OpenAPI spec and won't write one" as a case to skip. If your framework can export OpenAPI, that becomes the input. [docs]

**Can we run it in CI?**
Yes, the docs have pages for CI, GitHub Actions and GitLab. The Studio action posts a PR comment with the changed generated files. A simple pattern is to run generate and fail the build if `git diff` is not empty. That pattern is my suggestion, not documented there. Remember Node 22.22 or newer in CI. [docs, opinion]

**What about build time and memory?**
My tiny spec took about 200 ms. Kubb's own docs claim less memory than orval and HeyAPI and the smallest install, and the fastest full build on three of four specs they measured. Those are their benchmarks, so run it on your largest spec. [tested for the tiny spec, docs for the claims]

**Is our spec sent anywhere?**
The docs say Studio runs the generator on your machine and doesn't upload your spec. There is also a Telemetry reference page in the docs. Read it before adopting in a restricted environment, I haven't. [docs, not tested]

## Backend

**Does the spec have to be perfect?**
Garbage in, garbage out. Kubb trusts the spec. There is a `kubb validate` command that checks structural correctness, but it can't tell if the spec matches what your server really does. For that you need contract tests. [docs: validate command; opinion]

**What if we use tRPC or GraphQL?**
Different world. tRPC already shares types end to end, and GraphQL has its own codegen. Kubb is for OpenAPI. [opinion]

**Does it tell us when the API breaks a consumer?**
Indirectly. After regenerating, the TypeScript compiler shows what broke (I showed this in the demo). The Kubb Studio PR snapshots list which generated files changed in a PR. It is not a dedicated API diff tool. [tested for the compiler part, docs for Studio]

## Frontend

**Do we commit the generated code?**
The docs say the generated files belong to your project, and do not prescribe either way. My take: commit if you want reviewable diffs in PRs. Git-ignore it if you prefer to generate on install or in CI. In my POC I git-ignored it. [docs, opinion]

**Why does `id` come out as `bigint`?**
The spec says `int64`, and the default adapter maps that to `bigint`. But JSON responses contain plain numbers, so the type and the runtime value can disagree. The docs recommend `integerType: 'number'` for most JSON APIs, set on the OpenAPI adapter (`adapterOas`), not on the TS plugin. I haven't tried it in the POC. [docs, not tested]

**Does it support React Query, Vue Query, SWR?**
Yes, there are plugins for all three. My POC only used types, client and Zod. [docs, not tested]

**Can I customize names, folders, or code style?**
Yes. For example: output paths per plugin, grouping by tag, enum style (`asConst` by default, `enum`, `literal`...), `optionalType`, `type` vs `interface`. For deeper changes there are resolvers, macros, printers, or you can write your own plugin. [docs]

**Does it validate responses at runtime?**
It generates Zod schemas (I showed them in the output). Whether the generated client validates automatically with them, I haven't tested. The docs say it accepts any Standard Schema validator (Zod, Valibot, ArkType). [tested for generation, not tested for wiring]

**What happens to my manual edits in `src/gen`?**
They get overwritten. With `clean: true`, the folder is wiped on every run. Keep only generated files there, and put customization in the config or a plugin. [tested]

## QA

**Can QA use it for mocks and tests?**
There are plugins for MSW handlers, Faker data, and Cypress tests, all driven by the same spec. I haven't run them yet, but this is the part I'd explore next with QA. [docs, not tested]

**Does it check that the real API matches the spec?**
No. Mocks and clients follow the spec. If the spec is wrong, they are wrong too. Use contract tests against the real server. [opinion]

## Alternatives

**Why not orval, HeyAPI or openapi-typescript?**
They are good. Orval is the closest in breadth. HeyAPI validates requests and responses at runtime. openapi-typescript is the fastest if you only need types. Kubb leads on breadth (Cypress, Redoc) and status-code-aware responses. Pick based on what you need. [docs]

**What about openapi-generator?**
The Kubb comparison page doesn't cover it. From general knowledge it is a mature, multi-language generator written in Java, while Kubb is focused on the TypeScript and JavaScript ecosystem. [general knowledge, not from the docs]

**Is there anything AI-related?**
Yes: an MCP server that exposes your API and code generation, and a Claude Code integration. Some AI features (API skills) need the Pro plan. [docs, not tested]
